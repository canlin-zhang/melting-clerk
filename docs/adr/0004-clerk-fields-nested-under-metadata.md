# Clerk frontmatter fields live inside `metadata:`, not at top level

The clerk's fields (`type`, `status`, `tier`, `triggers`, `last_modified`, `archived`, `archive_note`) are written nested under `metadata:` in every memory file, leaving only `name` and `description` at the top level. This costs a one-time sweep of an existing store, and it is deliberate, because the natural-looking shape - flat top-level keys - is the unsafe one. A host that manages memory files itself may model a memory's frontmatter as exactly `{name, description, metadata}`; Claude Code's auto-memory does, and its rewrite path reconstructs frontmatter as `{...frontmatter.metadata, ...}`, so anything at top level sits outside what it spreads through and can be dropped when that path fires.

This was observed directly rather than inferred: an ordinary `Edit` to a memory file was followed by auto-memory rewriting that file's frontmatter - re-quoting `description` with escaped inner quotes, re-adding a field it tracks, and injecting session-provenance stamps - while preserving every clerk field, because they were nested by then and came through the spread. Two things to take from it. The rewrite fires on plain edits, not only on the usage-statistics path, so the absence of statistics keys in a store is **not** evidence that it has never fired. And enforcement therefore cannot live behind a tool call: the host writes with its own file tools, so only a write-time hook sees every write.

`memorylib.parse_frontmatter` flattens `metadata:` contents into the same namespace as top-level keys, so nesting is a no-op for the clerk and the whole cost is the migration. Do not "simplify" these fields back to top level - it reads cleaner and silently re-opens the hole. `past_projects/` is exempt: purely archival, updated only when touched.
